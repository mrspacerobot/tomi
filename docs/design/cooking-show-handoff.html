Cooking Show handoff

Every token the Cooking Show mockups use, for the design system work of #194. The mockups are round 13 (all 37 screens), round 14 (real photos) and round 15 (18 more screens). The two lightings are the morning show (light appearance) and the evening show (dark appearance). Names in the Token column are the CSS variables of the mockups, so a value can be found in them; #194 gives each its ColorRole, TextStyle, Spacing, Radius or RuleWeight name.

Sizes are mockup pixels. The mockup screen is 282 px wide; an iPhone 17 is 402 pt wide, so a mockup pixel is about 1.43 points. #194 settles the point values, with text sizes mapped onto Dynamic Type so they grow with the cook's text size.

Only the screens count. The page around them (Inter, beige page, the "What should change?" box) and the earlier kit classes the screens no longer use (path nodes, ticket stubs, comic panels, the kitchen backdrop) are not part of the look.

Text pairs to check in #194

The app holds every text pair to 4.5 to 1 (ColorRole.bodyTextPairings). Measured on the mockup values; those marked fail must change colour in #194, never the test.

The app uses #945100 for morning stage labels and #C02F1B for red surfaces carrying text and red text on light cards. The mockup red stays available for decorative marks. The green answer key uses ink text. These values keep the marquee kicker, chip, button and tab treatments readable in both lightings.

Type

Two families, both SIL Open Font License: Lilita One 400 for anything that announces (titles, the sign, buttons, card titles, numbers) and Nunito 700, 800 and 900 for everything you read. The mockups never set Nunito lighter than 700. Inter appears only in the drawn status bar and the page around the phones. Text is never uppercase in the data; caps are styling (.textCase(.uppercase)).

Motion and feel

From round 13's Feel section. Each haptic fires from the same animation timeline as the motion, follows the phone's System Haptics setting, and is never the only signal. Reduce Motion stops the motion and keeps the haptic. SwiftUI's sensoryFeedback covers the simple ones; the custom patterns need Core Haptics behind a service, like voice and camera.
